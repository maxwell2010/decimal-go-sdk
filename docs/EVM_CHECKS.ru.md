# Подпись погашения EVM Checks

[English](EVM_CHECKS.md) | [Официальные JS-исходники](CHECKS_JS_EVIDENCE.md) | [Исходники ноды](CHECKS_NODE_EVIDENCE.md)

**Совместимость подписи с deployment не подтверждена.** Локальное исполнение показало: исторический bytecode Checks из закреплённого JS SDK проверяет personal-подпись только хеша чека, а помощник следует JS-исходнику с привязкой к получателю. Этот артефакт отклоняет подпись помощника. Наблюдённый публичный runtime отличается от артефакта. ABI и размер кода не определяют схему подписи публичного deployment. См. [результаты исполнения](LOCAL_EVM_TESTS.ru.md).

Помощник воспроизводит подтверждённый формат официального JS SDK. Это отдельный протокол от исторических Cosmos/RLP-чеков, ERC20 permit и Safe. Помощники не вызывают RPC, не подписывают блокчейн-транзакцию и ничего не отправляют.

## Подтверждённый формат

Официальный JS получает ключ подписанта чека как `keccak256(UTF8(password))`, предварительно отклоняя пустой пароль. `EVMCheckSignerFromPassword` возвращает переиспользуемый `KeySigner`, а не приватный ключ. Некорректный UTF-8 отклоняется, нормализация Unicode не выполняется. Это прямое хеширование пароля, а не KDF для усиления паролей. Публичные пароли примеров являются фикстурами и не должны управлять средствами.

Для погашения JS объединяет непрозрачный 32-байтовый хеш чека и 20-байтовый адрес получателя, вычисляет Keccak256 от 52 байт и вызывает Wallet.signMessage для 32 байт результата:

```text
inner  = keccak256(checkHash[32] || redeemer[20])
digest = keccak256("\x19Ethereum Signed Message:\n32" || inner[32])
```

`EVMCheckRedemptionHash` возвращает inner, `EVMCheckRedemptionDigest` возвращает digest. Callback подписывает уже готовый digest. Повторный personal-sign или подпись текстовой hex-строки дадут другой результат. Подпись возвращается как 65 байт с canonical low-S и v=27/28; результат callback с v=0/1 нормализуется после проверки.

Помощник не добавляет chain ID, адрес контракта, nonce, сумму или срок. Он не устанавливает, входят ли эти данные внутрь непрозрачного checkHash. Нельзя выдумывать алгоритм checkDetailsHash по полям ABI. Нода подтверждает отдельную формулу хранимого идентификатора `keccak256(checkDetailsHash || signer)`, но не первоначальное вычисление checkDetailsHash.

## Полный запускаемый пример

```sh
go run ./examples/checks_signing
go test ./examples/checks_signing
```

[Полный Go-код](../examples/checks_signing/main.go) создаёт подписанта из публичного пароля, подписывает фикстуру для конкретного redeemer, проверяет восстановленный адрес и собирает redeemChecks. Хеш в примере не получен из выпущенного чека. Вывод содержит только хеш фикстуры, адрес подписанта и длину calldata. Пример не подтверждает наличие deployment, средств или возможность погашения.

Фрагмент для функции приложения:

```go
signer, err := decimal.EVMCheckSignerFromPassword(password)
if err != nil { return err }
defer signer.Close()
signature, err := decimal.SignEVMCheckRedemption(ctx, signer, checkHash, redeemer)
if err != nil { return err }
if err = decimal.VerifyEVMCheckRedemption(checkHash, redeemer, signer.Address(), signature); err != nil { return err }
checks, err := new(decimal.Client).Checks(checksAddress) // только офлайн-сборка
if err != nil { return err }
call, err := checks.BuildSignedRedemption(redeemer, []decimal.EVMCheckRedemptionProof{
    {CheckHash: checkHash, Signer: signer.Address(), Signature: signature},
})
if err != nil { return err }
_ = call // Send и Broadcast не вызываются
```

Импорт: `decimal "github.com/maxwell2010/decimal-go-sdk"`. ctx, password, checkHash, redeemer и checksAddress явно передаёт приложение. `SignEVMCheckRedemptionWith` поддерживает внешний callback подписи digest и ожидаемый адрес подписанта. Неправильный ключ, некорректная подпись и отмена контекста отклоняются. Возвращаемые буферы подписи являются отдельными копиями.

## Роли при создании и погашении

- В signers[] создания передаётся адрес **подписанта чека**, полученного из пароля. Создатель финансирует чек; его адрес не обязан совпадать с подписантом. Комментарии ноды подтверждают сумму DEL как amount, умноженную на число подписантов. Token permit остаётся отдельным разрешением ERC20.
- Зафиксированный JS ABI содержит nonces() без аргумента адреса. При этом миграция ноды описывает хранение nonce по адресам. Это наблюдения о разных исходниках/поколениях, а не взаимозаменяемые getters и не доказательство глобального nonce каждого deployment. Помощник не читает и не угадывает nonce, dueBlock, сумму, токен или deployment; выбранный контракт проверяется отдельно.
- Настоящий идентификатор получают из результата создания/симуляции проверенного deployment либо события CreatedCheck. ABI и состояние проверяются отдельно. Помощник не создаёт существующий чек из произвольных полей.
- **Redeemer** - аккаунт прямого вызова погашения в официальном JS-профиле и получатель выплаты. Для прямого вызова используйте этот же аккаунт как отправителя. Офлайн-calldata не закрепляет From. Вызовы через Safe, relayer или другой контракт требуют отдельной проверки непосредственного caller; этот помощник не подтверждает такие маршруты.
- BuildSignedRedemption проверяет каждую подпись для redeemer и заявленного подписанта чека, отклоняет повторные хеши и сохраняет порядок. Это не проверка выпуска, срока, средств, allowance или полномочий в состоянии сети.

Чистые Hash/Digest поддерживают все значения фиксированной длины. Подпись и проверка proofs дополнительно отклоняют нулевые адреса redeemer и expectedSigner как правило использования SDK. Оно не выдаётся за независимо доказанное правило контракта.

Тесты SDK используют реально выполненные официальные ethers-векторы с ASCII, Unicode, NUL и обоими recovery ID. [Фикстуры](checks-js-vectors.json). Реализован проверенный JS-профиль подписи, а не универсальный интерфейс всех поколений контрактов ноды.

Приёмка текущего deployment и полнота Solidity-исходников остаются отдельными границами доказательств. Транзакции в сеть при этой реализации не отправлялись.

Результат callStatic при создании является прогнозом, а не выпуском или финансированием чека. Прежде чем считать хеш существующим погашаемым чеком, подтвердите фактическое событие создания и состояние.
