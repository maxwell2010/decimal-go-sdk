# Weighted Safe and allowance workflows

`PackWeightedSafeSignatures` supports typed EIP-712 EOA signatures, explicit personal-message signatures and contract signatures. It verifies EOA recovery against declared owners, rejects duplicates/non-owners, checks the policy nonce and weighted threshold, and sorts owners numerically. Contract signatures require a deployment-specific verifier callback; a callback returning an error prevents packing. The SDK does not assume that every EIP-1271 deployment uses the same function signature or magic value.

Packing follows official [dsc-js-sdk execution.ts](https://bitbucket.org/decimalteam/dsc-js-sdk/src/6790d35e2decb0cbb06a9149a9c476c834f99223/src/decimalevm/multisig/execution.ts#lines-154): each static entry is 65 bytes, contract entries use signer/offset/type-zero, and dynamic tails are length-prefixed without invented padding. Multiple contract offsets, input snapshotting and personal-message domains have regression tests. `SafeTransaction.SigningPreimage` supplies the 66-byte EIP-712 envelope for legacy bytes-based signature verifiers; its Keccak256 matches `SafeTransaction.Hash`.

`Contract.ReadSafePolicy(ctx, block)` reads `getOwnersWithWeights`, `getWeightThreshold` and `nonce` at the same explicit block. These selectors are confirmed by the public testnet Safe ABI imported as `TestnetSafe20261029`; see `additional-deployment-sources.json`. No owner getters are fabricated for other contract generations. This policy adapter intentionally follows the official JS owner-weight range 1..1000 and rejects larger values rather than truncating uint256 ABI output. Low-level ABI readers remain available for other weight policies. A policy snapshot is not evidence of authorization or freshness at a later execution block.

For the full ABI width use `ReadBigSafePolicy` and `PackBigWeightedSafeSignatures`. `BigSafePolicy` retains owner weights and threshold as uint256-range `big.Int` values, snapshots every numeric/map/signature input and validates positive weights, threshold <= total, uint256 sum overflow, duplicates and nonce. It then shares the same cryptographic verification and signature wire encoder. Tests include weights beyond 2^64, invalid 2^256 thresholds, total overflow and mutation from an untrusted verifier callback. The older bounded helper remains available for compatibility with official JS UI constraints.

`PlanERC20Allowance(..., resetExisting=true)` produces zero-approval then target-approval when an insufficient nonzero allowance must first be reset. Approvals and action are separate EOA transactions. Confirm each approval before preparing the next step and re-read allowance if another process can change it. The planner snapshots mutable action data and performs no signing or broadcasting. No approvals are created when the existing allowance is sufficient. Known generic Multicall allowance routes remain rejected.

No network transactions were sent while implementing or testing these helpers. Local tests verify encoding/authorization inputs and error behavior, not deployed Safe execution or token-specific acceptance.

`Client.ContractSignatureVerifier` provides explicitly selected modern ERC-1271 `isValidSignature(bytes32,bytes)`/`0x1626ba7e` and legacy Safe `isValidSignature(bytes,bytes)`/`0x20c13b0b` adapters. It requires a supplied ABI, explicit snapshot block, nonempty owner code and exact magic response. Legacy callers supply a preimage that must hash to the requested digest. There is no automatic probing/fallback. Sources: [ERC-1271 specification](https://eips.ethereum.org/EIPS/eip-1271), [Safe v1.3.0 interface](https://github.com/safe-global/safe-smart-account/blob/v1.3.0/contracts/interfaces/ISignatureValidator.sol). A top-level eth_call does not prove identical nested STATICCALL behavior or future state; simulate the intended Safe check/execution context before submission.

## Sender-restricted token batch adapter

`RestrictedMultisend` ports the interface and validation from the local C# `csharp/src/Decimal.Web3/Multisend/CandySafeMultisend.cs`. That source records the reviewed runtime hash `0x7784c7a41662304b6f6c183f2169a9b6844a1a2f192021d8f3d1ccbdacfc821e`, mainnet address `0x9b0658e219636215f7f78a88c241ef3bbff447a9`, and testnet address `0xf5d23ad4ba70d22554d25bcfe9bae2af828a6ea4`. These are local C# evidence, not newly verified Go mainnet deployments or official Decimal defaults. The Go constructor requires an explicit address/chain/runtime hash; the old arbitrary-Multicall route remains disabled.

`BuildToken` and `BuildTokenWithPermit` construct the explicit sender-restricted ABI offline. `Verify` checks chain and actual runtime codehash. `PrepareToken` additionally verifies token balance and allowance. `PrepareTokenWithPermit` verifies balance, the token's actual nonce/domain separator and recovery of an owner-bound signature over the exact total and deployment spender. Both prepare methods perform fee preparation only. Inputs enforce 1..500 positive payouts, uint256 totals, nonzero/non-self/non-contract recipients and at most 256 UTF-8 memo bytes. Neither constructor nor builder implies deployment verification; callers who bypass Prepare must explicitly verify the runtime and token authorization. Runtime verification is a snapshot, not a guarantee against later code/state changes.
